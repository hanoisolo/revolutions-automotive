### SEGMENT 1 — ENGINE EXTENSIONS (`revolutions_engine.js` + `test_revolutions.js`)

**Code files (2):** `revolutions_engine.js`, `test_revolutions.js`.
Everything below is added to the existing dual UMD engine without touching
existing exports or behavior.

**New data structures:**

1. `DIAGNOSTIC_DECISION_TREE` — frozen multi-step "What's That Noise /
   Warning Light?" narrowing tree. Define its exact node schema (id, prompt
   text, question type, options with next-node pointers, terminal diagnosis
   nodes). Terminals must reference existing `SERVICE_CATALOG` service IDs
   (e.g. `diag_computer_scan`, `diag_elec_parasitic`, `brk_pads_rotors`,
   `tir_align_4whl`, `tune_spark_induction`) plus a triage outcome.
2. `MTO_SSC_CHECKLIST_ITEMS` — frozen array covering exactly **11 Ontario
   Safety Standards Certificate inspection areas** (brakes, tires, front
   steering & suspension, rear suspension/frame, lighting, windshield &
  glass, wipers, horn & signaling, mirrors, exhaust/emissions, body/
   structural). Each item schema must include id, area label, plain-language
   homeowner inspection question(s), weight, and severity classification.
3. `SEED_WORK_ORDERS` — frozen array of at least 3 sample work orders in
   different states, including at minimum:
   - `REV-2048` — currently `IN_REPAIR_BAY`
   - `REV-3105` — currently `PARTS_ORDERED`
   - `REV-4092` — currently `READY_FOR_PICKUP`
   Define the work-order state machine states: `CHECKED_IN`,
   `ON_HOIST_DIAGNOSTICS`, `PARTS_ORDERED`, `IN_REPAIR_BAY`,
   `QUALITY_ROAD_TEST`, `READY_FOR_PICKUP`.

**New pure functions (exact contracts required in the roadmap):**

1. `evaluateDiagnosticWizard(answersObject)` — returns
   `{ triageLevel, likelyCauses, recommendedServiceId, technicianNotes }`
   where `triageLevel` is exactly one of
   `"tow_now" | "schedule_urgent" | "routine_inspect"`. Specify the input
   answer-key schema and every decision rule.
2. `evaluateSafetyPreCheck(answersObject)` — returns
   `{ scorePercentage (0–100), status ("pass" | "fail" | "advisory"),
      criticalFailures[], recommendedServices[] }`. Specify the exact
   scoring formula (weighted items, critical-item auto-fail rules).
3. `lookupWorkOrder(query, phoneOrPlate)` — matches a work order by code,
   phone, or license plate; returns the full work-order object or `null`.
   Specify matching rules and normalization (case, whitespace, plate
   format).
4. `createWorkOrder(bookingPayload, estimatePayload)` — builds a new
   persistent work order with a unique `REV-XXXX` code (4-digit, zero
   collision with seed codes), initial state `CHECKED_IN`, derived fields
   from the booking and estimate payloads, and deterministic timestamp
   handling (specify how, since `Date.now()` must remain testable).

**Unit tests (additive only):** 25+ new headless `assert` assertions in
`test_revolutions.js` raising the total from 91 to **116+**, covering all
four functions, all data structure invariants, the state machine, and edge
cases (unknown query, invalid answers, tow_now triggers, 0 and 100 scores,
work-order code uniqueness).

**Gate:** `node test_revolutions.js` — 116+ PASSED, zero prior tests
removed or weakened.
